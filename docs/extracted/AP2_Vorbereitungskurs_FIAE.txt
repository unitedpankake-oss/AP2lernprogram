Übung 1
Erstelle für HelpDesk Pro eine Tabelle mit vier Stakeholdern. Nenne je eine Erwartung, eine Befürchtung und eine Maßnahme. Markiere den Stakeholder mit dem größten Projektrisiko.

REST-Prinzipien
Ressourcen als Substantive und plural benennen, z. B. /tickets statt /createTicket.
Stateless: Jede Anfrage enthält die nötigen Informationen; keine versteckte Sitzungsvoraussetzung.
Idempotenz: GET, PUT und DELETE sollen bei Wiederholung denselben beabsichtigten Zustand erzeugen; POST ist typischerweise nicht idempotent.
Content-Type beschreibt den gesendeten Body; Accept die gewünschten Antwortformate.
Authentifizierung (401) und Autorisierung (403) unterscheiden.

MODUL 10  |  105 Minuten
Pseudocode für Klassenmethoden
Lernziel: Vorgegebene Methodensignaturen vollständig, robust und nachvollziehbar in sprachneutralem Pseudocode implementieren.

Pseudocode wird nach Logik bewertet, nicht nach einer konkreten Programmiersprache. Verwende eindeutige Zuweisungen, Bedingungen, Schleifen, Rückgaben und Fehlerbehandlung.
METHOD statusAendern(neu: TicketStatus): Boolean    IF neu IS NULL THEN        RETURN FALSE    ENDIF    erlaubteUebergaenge <- {        NEU: [ZUGEWIESEN, STORNIERT],        ZUGEWIESEN: [IN_BEARBEITUNG, STORNIERT],        IN_BEARBEITUNG: [WARTET, GELOEST]    }    IF neu NOT IN erlaubteUebergaenge[this.status] THEN        RETURN FALSE    ENDIF    this.status <- neu    this.geaendertAm <- NOW()    RETURN TRUEENDMETHOD

Robuste Lösungsstruktur
Vorbedingungen und Sonderfälle prüfen.
Benötigte Variablen initialisieren.
Kernalgorithmus mit klaren Bedingungen/Schleifen umsetzen.
Objektzustand nur konsistent ändern.
Ergebnis oder Fehler eindeutig zurückgeben.
Typischer Fehler: Die Methode soll einen Wert zurückgeben, aber ein Ausführungspfad endet ohne RETURN. Prüfe alle Zweige.

MODUL 12  |  90 Minuten
Datenschutz und DSGVO
Lernziel: Rechtsgrundlage, Einwilligung, Betroffenenrechte, Datenminimierung und sichere Passwortspeicherung prüfungstauglich erläutern.

Grundprinzipien
Rechtmäßigkeit, Transparenz und Zweckbindung: Daten nur für einen festgelegten legitimen Zweck verarbeiten.
Datenminimierung: nur erforderliche Daten erheben.
Richtigkeit und Speicherbegrenzung: Daten aktuell halten und löschen/anonymisieren, wenn der Zweck entfällt.
Integrität und Vertraulichkeit: angemessene technische und organisatorische Maßnahmen.
Rechenschaftspflicht: Einhaltung nachweisen können.
Wirksame Einwilligung
Eine Einwilligung muss freiwillig, informiert, zweckgebunden, eindeutig und widerrufbar sein. Sie darf nicht unnötig an eine Leistung gekoppelt werden. Für zwingend notwendige Vertragsverarbeitung ist häufig Vertragserfüllung statt Einwilligung die passendere Rechtsgrundlage.
Passwörter speichern
Richtig
Falsch
langsamer, geeigneter Passwort-Hash wie Argon2id, bcrypt oder scrypt
Klartext oder reversible Verschlüsselung
zufälliger individueller Salt pro Passwort
ein gemeinsamer fester Salt
Kostenparameter regelmäßig prüfen und Hash bei Login aktualisieren
schneller Hash wie MD5 oder SHA-256 allein
Zugriff beschränken, TLS bei Übertragung, Rate Limiting und MFA erwägen
Passwort per E-Mail versenden oder protokollieren

Wichtig: Salting verhindert gleiche Hashes bei gleichen Passwörtern und erschwert vorberechnete Tabellen. Es ersetzt keinen langsamen Passwort-Hash. Ein Pepper kann zusätzlich getrennt vom Datenbestand als Geheimnis gehalten werden.

Lernziel: Einen Sortieralgorithmus in Pseudocode mit einer vorgegebenen compare(a,b)-Funktion korrekt umsetzen.


Bubble Sort: Ein vollständiger Durchlauf verschiebt das größte Element nach hinten
METHOD bubbleSort(items, compare)    IF items IS NULL THEN RETURN    n <- LENGTH(items)    REPEAT        swapped <- FALSE        FOR i <- 0 TO n - 2            IF compare(items[i], items[i + 1]) > 0 THEN                SWAP(items[i], items[i + 1])                swapped <- TRUE            ENDIF        END FOR        n <- n - 1    UNTIL swapped = FALSE OR n <= 1ENDMETHOD

Konvention: compare(a,b) < 0 bedeutet a steht vor b; = 0 gleichwertig; > 0 a steht nach b. Bei Vertauschung nur für > 0 bleibt Bubble Sort stabil. Laufzeit: durchschnittlich/schlechtestenfalls O(n²), mit Abbruch im besten Fall O(n).

MODUL 22  |  75 Minuten
Pfade für Pfadüberdeckung aufzählen
Lernziel: Kontrollflussgraphen systematisch lesen und vollständige Start-Ende-Pfade ohne Auslassungen notieren.

Vorgehen: Knoten eindeutig benennen, jede Entscheidung mit ausgehenden Kanten markieren, vom Start aus jeweils eine Kante verfolgen und erst am Ende den vollständigen Pfad notieren. Danach an der letzten noch nicht variierten Entscheidung zurückgehen.
P1: B1 – A1 – B2(T) – A2 – B3(T) – A4 – EP2: B1 – A1 – B2(T) – A2 – B3(F) – EP3: B1 – A1 – B2(F) – A3 – B3(T) – A4 – EP4: B1 – A1 – B2(F) – A3 – B3(F) – E

Bei zwei unabhängigen binären Entscheidungen entstehen maximal 2² = 4 Kombinationen. Abhängige Guards oder frühzeitige Returns können Kombinationen unerreichbar machen. Schleifen werden für begrenzte Pfadtests häufig mit 0, 1 und mehreren Durchläufen betrachtet.
Typischer Fehler: Eine Folge wie B1–B2–B3 ist nur dann ein Pfad, wenn die Kanten im Graphen wirklich existieren. Aktionen zwischen Entscheidungen dürfen nicht weggelassen werden, wenn Knoten vollständig aufzulisten sind.

IF comments IS NULL OR date IS NULL THEN RETURN 0; count←0; FOR EACH c IN comments: IF c IS NOT NULL AND c.erstelltAm > date THEN count←count+1; ENDIF; END FOR; RETURN count.

19 – Sortieren
compare(a,b): Prioritätsrang höher soll zuerst stehen. Wenn rank(a.priority) != rank(b.priority), RETURN rank(b)-rank(a). Sonst RETURN compareDate(a.erstelltAm,b.erstelltAm).

21 – Coverage
Gemeinsame Anweisungsüberdeckung: 11/12 = 91,7 %. Gemeinsame Zweigüberdeckung: 3/4 = 75 %.
Die Prozentwerte werden über unterschiedliche erreichte Elemente gebildet, nicht durch Addition der Einzelwerte.
22 – Pfade
Mit B4 entstehen aus jedem bisherigen Pfad, der A4 erreicht, zwei Varianten: ...–A4–B4(T)–A5–E und ...–A4–B4(F)–E. Pfade über B3(F) erreichen B4 nicht.
Ein minimales Set für Zweigüberdeckung muss B2 T/F, B3 T/F und – sofern B3(T) – B4 T/F enthalten; mindestens vier passend kombinierte Pfade sind eine naheliegende Lösung.
23 – Unit/Regression
Arrange: Ticket im Zustand NEU. Act: result←statusAendern(GESCHLOSSEN). Assert: result=false und status=NEU.
Als Regressionstest verhindert er, dass eine spätere Änderung die Zustandsregel wieder umgeht; er läuft automatisiert bei jeder relevanten Änderung.
24 – Bug finden
Fehler: count startet bei 1 (Off-by-one), Bedingung zählt GESCHLOSSEN statt offene Zustände, RETURN im Schleifenkörper beendet beim ersten Treffer.
Korrektur: count←0; gesamte Liste durchlaufen; bei status in [NEU,ZUGEWIESEN,IN_BEARBEITUNG,WARTET] erhöhen; erst nach der Schleife zurückgeben.
25 – OOP
MessageSender definiert send(message):Result. EmailSender und SmsSender implementieren das Interface.
Eine abstrakte BaseSender-Klasse ist sinnvoll, wenn gemeinsames Rate-Limit/Logging echten Zustand und Basislogik teilt. Der Aufrufer arbeitet mit MessageSender; zur Laufzeit wird die konkrete send-Implementierung dynamisch gewählt.
26 – Kryptografie
Backup: symmetrisch verschlüsseln, Schlüssel getrennt schützen → Vertraulichkeit.
Passwort: Argon2id/bcrypt/scrypt + individueller Salt → erschwerte Offline-Angriffe.
Softwareupdate: digitale Signatur prüfen → Authentizität und Integrität. HTTPS: TLS mit Zertifikat/(EC)DHE und symmetrischen Sitzungsschlüsseln.
27 – Normalisierung
KUNDE(kunde_id PK,kunde_name,kunde_ort); KATEGORIE(kategorie_id PK,kategorie_name); TAG(tag_id PK,tag_name); TICKET(ticket_id PK,kunde_id FK,kategorie_id FK); TICKET_TAG(ticket_id PK/FK,tag_id PK/FK).
Abhängigkeiten kunde_id→Kundendaten, kategorie_id→kategorie_name, tag_id→tag_name werden ausgelagert. Dadurch verschwinden redundante Updates; Tags können ohne Ticket angelegt und letzte Zuordnungen ohne Informationsverlust gelöscht werden.
28 – GRANT
CREATE VIEW reporting_ticket AS SELECT t.ticket_id,t.status,k.kunden_id,k.name FROM ticket t JOIN kunde k ON k.kunden_id=t.kunden_id; GRANT SELECT ON reporting_ticket TO reporting_role.
GRANT SELECT ON ticket TO support_role; GRANT UPDATE(status,bearbeiter_id) ON ticket TO support_role; REVOKE DELETE ON ticket FROM support_role. Syntax/Spaltenrechte hängen vom DBMS ab.
29 – Migration
Risiken: Dubletten, Datumsformate, Statusmapping, verwaiste FKs, Encoding, Volumen und Datenschutz.
Lösungen: Staging, Deduplizierungsregel, kanonisches Datum, freigegebene Mappingtabelle, Quarantäne für Fehler, Batch-Import, Backup/Rollback.
